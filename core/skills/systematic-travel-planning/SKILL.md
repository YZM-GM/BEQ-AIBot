Systematic Travel Planning (STP) - 系统化旅行规划

概述 (Overview)
旅行规划本质上是一个涉及“时空约束条件”与“资源调度分配”的运筹学工程问题。
严禁盲目输出文字堆砌的行程表。必须遵循标准流程：首先验证约束条件，其次计算空间拓扑（物流通勤），最后进行时间装箱（行程生成）。

核心原则：如果你没有对“通勤时间”与“人类体力极限”进行过明确的计算与校验，你生成的行程计划纯属“模型幻觉（Hallucination）”。

何时使用 (When to Use)
当用户提出以下意图时，必须无条件触发：
- “帮我规划去 X 地的旅行”
- “给我一份 Y 城市的3日游攻略”
- 要求修改、评估或优化现有的旅行路线

绝对铁律 (The Iron Law)
没有明确的通勤与空间校验，绝不允许生成行程。
（NO ITINERARY WITHOUT EXPLICIT LOGISTICS VALIDATION）

反瞬移法则：人类无法瞬间移动。忽视此物理法则生成的计划即为无效废品。如果你将地点 A 和地点 B 安排在相邻的顺序，却不知道它们之间的精确通勤时间、交通工具以及必要的缓冲时间，立即停止生成。删除代码/文本。先计算空间通勤。

阶段一：约束 (CONSTRAINTS) - 边界采集
在编写任何时间表之前，你必须提取或向人类用户询问以下“核心参数”：
1. 时间窗口：精确的日期、具体的抵达/离开航班或高铁时间（这决定了首日与末日的可用时间基数）。
2. 预算约束：穷游/背包客、标准舒适、豪华/不设上限。
3. 能量吞吐率（节奏）：
   - 休闲 (Relaxed)：每天 1-2 个核心兴趣点（POI），极度宽裕。
   - 标准 (Standard)：每天 3-4 个 POI，劳逸结合。
   - 特种兵 (Aggressive)：每天 5+ 个 POI，高强度极限拉练。
4. 团队人口统计：单人、情侣、长者同行、带婴幼儿（长者与儿童决定了强制休息机制的触发频率）。
5. 硬性依赖：用户指定“必须打卡”的地点或活动。

*行动指令：* 如果参数缺失，严禁自我猜测。立即向用户提问以补全上下文。

阶段二：拓扑 (LOGISTICS) - 空间验证
将所有地点视为图论中的“节点 (Nodes)”，将交通通勤视为“有向边 (Directed Edges)”。你必须在后台计算：
- 节点滞留时间 (Node Duration)：体验该节点所需的真实时间下限（例如：北京故宫 = 最少4小时，而非1小时）。
- 边际成本 (Edge Cost)：物理距离 + 交通工具属性 + 步行与等车时间。
- 营业时空门：预估抵达时，该节点是否处于开放状态？

*规则：* 如果你缺乏精确的地图数据，必须显式声明你的估算假设（或者，通过触发 MCP 工具调用外部地图 API 进行计算）。

阶段三：行程 (ITINERARY) - 时间装箱
使用严格的“时间盒 (Time-boxing)”机制起草行程。

<Good>
第一天：巴黎历史轴线
- 09:00 - 13:00 [节点] 卢浮宫（需消耗极高体力）
- 13:00 - 14:30 [边/缓冲] 附近午餐 + 步行至巴黎圣母院（预留30分钟通勤）
- 14:30 - 16:30 [节点] 巴黎圣母院与西岱岛
- 16:30 - 18:00 [边] 乘坐地铁4号线前往蒙马特高地 + 咖啡馆休息恢复体力
</Good>

<Bad>
第一天：
- 上午：卢浮宫、埃菲尔铁塔、凯旋门
- 下午：凡尔赛宫
（判定：严重违反物理空间距离与人类体力极限。立即删除并重构。）
</Bad>

阶段四：优化 (OPTIMIZATION) - 系统容错
一个健壮的系统必须能够处理异常。你的计划必须包含：
- 缓冲注入 (Buffer Injection)：在主要的地点转换之间，强制增加 15-30 分钟的弹性时间。
- 降级预案 (Fallback/Plan B)：如果某日安排了高密度的户外行程，遇暴雨时的室内替代方案是什么？
- 餐饮地理集成：严禁在地理“死角”（如荒郊野岭、无商业区的纯景区周边）安排午餐，除非自带干粮。

质量评估矩阵
| 评估维度 | 优质标准 (Good) | 劣质特征 (Bad) |
| :--- | :--- | :--- |
| 密度边界 | 严格遵守用户的“能量吞吐率” | 试图在5天内塞入6个不同城市 |
| 物理通勤 | 标注明确的通勤方式与耗时（例：地铁45分钟） | 隐式触发“瞬移”（例：接下来，去...） |
| 作息贴合 | 每天的开始时间符合人类常理（如早9点） | 默认游客在休假期间每天早晨6点起床 |
| 资源补给 | 分配了具备明确地理位置的餐饮与休息时间块 | 完全忽略人类需要吃饭和上厕所 |

常见的合理化借口（防范认知反模式）
借口 | 现实真相
"用户可能只是想要个地点推荐列表" | 列表不等于行程。请询问他们是需要列表还是具体的日程安排。
"我先假设他们会打车过去" | 出租车会遇上早晚高峰，地铁有固定班次。必须在行程中明确定义交通工具的边界条件。
"如果他们走快点，一天看5个博物馆是可行的" | 违反正常人类体力规律。除非用户明确声明“特种兵”模式，否则默认按“标准”节奏执行。
"我无法获取准确的高铁时刻表" | 使用经验估算并向用户声明不确定性，或立即请求授权使用 MCP 查询实时接口。

红旗警告 - 立即停止并推翻重做
- 在不知道抵达和返程时间的情况下，生成了首日和末日的完整行程。
- 将两个物理距离 > 1小时的地点安排在一起，却未扣除相应的通勤时间。
- 行程中连续运转超过 6 小时，未安排任何进食与休息节点。
- 为带有婴幼儿的家庭，在本应作为休整的日期安排了高强度的徒步。
- 将一个核心景点的游览时间压缩到其体验下限以下（如：给大英博物馆仅分配 45 分钟）。
出现以上任何一种情况，意味着你绕过了系统约束。删除结果，退回“阶段一”重新执行。

系统校验清单 (Verification Checklist)
在向用户输出最终旅行计划前，系统必须通过以下内部断言：
[ ] 所有约束条件（日期、节奏、人群特征）已被显式确认并应用。
[ ] 每一个相邻节点之间的物理通勤时间已被计算并扣除。
[ ] 餐饮、休息的生理缓冲时间已被注入系统。
[ ] 每天的启动时间与结束时间符合生物学常理。
[ ] 核心高风险路径（如天气敏感型活动）已配备了降级预案 (Plan B)。

如果无法勾选全部清单，说明当前生成的计划是一个残次品。严禁输出，立即重构。
